# התקנה, פריסה ותפעול

## מבנה
- frontend: static/index.html, static/app.js, static/style.css
- backend/API: server.py (Flask)
- database: SQLite עם WAL, מפתחות זרים וטרנזקציות BEGIN IMMEDIATE
- migrations/001.sql: סכמה התחלתית. טבלת schema_versions מתעדת גרסאות.
- data/structure.json: 149 משניות לפי המספור המקובל; יומא ג׳ מכיל 11.
- data/samples.json: שש משניות מוכנות. השאר מקבלות תוכן חסר.
- tests/: בדיקות מקביליות, API, כרטיסים, סבבים וייבוא.

## התקנה מקומית (Python 3.12)
1. צרו סביבה וירטואלית והתקינו: `pip install -r requirements.txt`.
2. הגדירו ADMIN_PASSWORD (12 תווים לפחות), SCHOOL_CODE (6 לפחות), DATABASE_PATH ו-COOKIE_SECURE=0 בפיתוח HTTP בלבד. אין טעינה אוטומטית של .env; הדוגמה מתעדת את המשתנים.
3. הריצו `python server.py`; פתחו http://localhost:8000.
4. בדיקות: `python -m unittest discover -s tests -v`; `node --check static/app.js`.

## פריסה
השרת מחייב דיסק מתמשך. אין לפרוס SQLite על דיסק זמני או להריץ כמה עותקים נפרדים עם בסיסי נתונים נפרדים.
- Dockerfile מגדיר Gunicorn עם worker אחד ו-8 threads.
- render.yaml הוא Blueprint לפריסה ב-Render עם דיסק /data.
- צרו Blueprint מהמאגר, הזינו סיסמת מנהל וקוד בית הספר דרך ממשק הסודות של שירות האירוח בלבד.
- התצורה משתמשת בתוכנית בתשלום עם דיסק מתמשך. בדקו את העלות שמוצגת לפני אישור החיוב.
- לחלופין שרת Docker יחיד עם volume ב-/data ו-proxy המספק HTTPS.
- בפריסה הגדירו COOKIE_SECURE=1 והפעילו רק דרך HTTPS.
- SEED_DEMO=1 טוען רשימה פיקטיבית ושש דוגמאות רק בהפעלה הראשונה של בסיס הנתונים.
- קובץ render.yaml לבדו אינו מפרסם אתר. נדרש חשבון אירוח, אישור יצירת שירות ובדיקת פריסה.
- אין חשבון מנהל או קוד בית ספר קבוע בקוד. ללא משתנים מתאימים השרת לא עולה.

## כניסה והפרדת הרשאות
קוד בית הספר פותח גישה לרשימת הכיתות והשמות; לאחר מכן בוחרים שם.
הבחירה בשם אינה אימות זהות אישי. זו מגבלה מכוונת של תהליך הכניסה המבוקש: מי שמחזיק בקוד בית הספר יכול לבחור שם אחר. אם יידרש אימות אישי, יש להוסיף PIN אישי או SSO לפני שימוש כזה.
הסיסמה למנהל נפרדת; תלמיד אינו יכול לקבל תוכן ניהול או תשובות נכונות ב-API.
Sessions נשמרים כ-hash של token אקראי, עם HttpOnly, SameSite=Strict ו-CSRF.
אין שימוש ב-localStorage כמקור אמת.
רשימות תלמידים והגרלה זמינות רק אחרי כניסה; אין להזין מידע אישי למאגר GitHub עצמו.

## ייבוא תלמידים
CSV ב-UTF-8 (אפשר לשמור מ-Excel כ-CSV UTF-8), או מערך JSON:
`id,name,class_id,class_name`
מזהים נשארים יציבים. ייבוא מזהה קיים מעדכן שם וכיתה, בלי למחוק כרטיסים או היסטוריית תרומות.
השבתת תלמיד נעשית בניהול ומבטלת sessions ונעילה קיימת. ייבוא אינו מפעיל אוטומטית תלמיד מושבת.
ייבוא אינו מוחק תלמידים חסרים. כשעוברים לנתונים אמיתיים, השביתו את חשבונות ההדגמה.
המנהל יכול לעדכן שם/כיתה באמצעות אותו ייבוא, גם של רשומה אחת.

## ייבוא משניות
JSON בלבד, לפי data/samples.json. ניתן להוריד מהניהול תבנית מלאה עם כל 149 המזהים.
מבנה רשומה:
```json
{"id":"rosh-hashanah:2:2","status":"ready","text":"טקסט מנוקד","questions":[
 {"prompt":"שאלה א","options":["א","ב","ג","ד"],"correct":"א"},
 {"prompt":"שאלה ב","options":["א","ב","ג","ד"],"correct":"ב"}
]}
```
- status: missing / review / ready.
- ready מחייב טקסט ושתי שאלות; לכל שאלה ארבע אפשרויות שונות ותשובה הנמצאת ברשימה.
- אין לשנות מזהים. המסכת, הפרק והמשנה נקבעים על פי המזהה הקנוני.
- בדיקת קובץ מציגה רשומות חסרות גם בייבוא חלקי; בייבוא מלא חוסר הוא שגיאה חוסמת.
- כל הקובץ עובר validation לפני שינוי; שגיאה כלשהי מונעת את הייבוא.
- שמירת ייבוא מבצעת validation שוב בצד השרת בתוך טרנזקציה.
- רק טבלת content מתעדכנת. תוכן של לימוד שכבר נפתח נשמר כ-snapshot עד סיומו; המשנה הבאה תשתמש בגרסה החדשה.
- עדכון למצב missing אינו מבטל השלמות היסטוריות.
- ניתן לערוך רשומת JSON בודדת בממשק הייבוא בלי שינוי קוד.

## סבבים ותיקונים
- כל השלמה פעילה ייחודית ל-(round_id,mishnah_id).
- כרטיס נרשם באותה טרנזקציה כמו השלמה.
- בקשה חוזרת לאותה תשובה לא מעניקה כרטיס נוסף.
- לאחר 149 השלמות בסבב הראשון נפתח בונוס אוטומטי. סיום שש דוגמאות אינו פותח בונוס.
- לאחר הבונוס אפשר לפתוח סבבים נוספים בניהול. אין מגבלת סכימה למספר הסבבים.
- תרומת כיתה ולוח כרטיסים מצטברים על פני כל הסבבים; מד ההתקדמות מציג את הסבב הנוכחי.
- ביטול השלמה מתועד ומפחית כרטיס, תוך שמירת הרשומה המקורית.
- ביטול השלמה בסבב סגור אינו פותח אותו מחדש ואינו מוחק סבב בונוס. ההיסטוריה מציגה את הביטול.
- אם יתרת התלמיד כבר אפס עקב תיקונים ידניים, יש לתקן את היתרה לפני ביטול השלמה.

## גיבוי
הריצו מתוך שרת האירוח:
`python scripts/backup.py /data/game.db /path/to/private-backups/game-YYYYMMDD.db`
הסקריפט משתמש ב-SQLite backup API ולכן תומך בבסיס נתונים חי וב-WAL.
יש להעביר את הגיבוי למקום פרטי נוסף, מחוץ לשרת ולמאגר, ולתזמן גיבוי יומי אצל ספק האירוח.
גיבויים מכילים מידע אישי. הגבילו גישה. ייצוא CSV אינו גיבוי מלא.

## שחזור
1. עצרו את שירות הכתיבה.
2. שמרו עותק של בסיס הנתונים הנוכחי וכל קובצי WAL/SHM שלו לצורך חזרה לאחור.
3. העתיקו את קובץ הגיבוי התקין ל-DATABASE_PATH. הסירו קובצי WAL/SHM ישנים רק לאחר שמירתם וכשהשירות כבוי.
4. התאימו הרשאות לבעל התהליך. הפעילו מחדש.
5. בדקו כניסת מנהל, מספר משניות, סבבים, יתרות כרטיסים והיסטוריית השלמות.
6. אל תריצו איפוס או seed נוסף על בסיס משוחזר.

## מגבלות אימות
נדרשות בדיקת CI מוצלחת, בדיקת דפדפן בטלפון, ובדיקת שני מכשירים על שרת חי לפני מסירה לתלמידים.
הבדיקות האוטומטיות מדמות לקוחות מקבילים מול אותו SQLite; הן אינן בדיקת מכשירים פיזיים.
